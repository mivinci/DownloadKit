## 今日工作

### 1. 修复 `xTaskGroupWait()` 概率性死锁（核心问题）

**现象**：Linux 容器中不带 `--verbose` 跑单测时，`TaskTest.GroupWait` 概率性卡死；带 verbose 时反而能通过。

**排查过程**：

1. 先在 macOS 和 Linux (gcc:14 容器) 上跑单测，发现 Linux 上不带 verbose 时测试会挂住
2. 用 `--verbose` 跑则通过 —— 怀疑 verbose 的 I/O 延迟改变了线程调度时序，掩盖了竞态条件
3. 定位到卡死发生在 `TaskTest.GroupWait` 测试用例
4. 分析 `task.c` 源码，发现 `xTaskGroupWait()` 和 idle worker 共用同一个 `qcond` 条件变量

**根因**：

`xTaskGroupWait()` 在 `qcond` 上 `pthread_cond_wait()`，idle worker 也在同一个 `qcond` 上等待新任务。当最后一个任务完成时，worker 调用 `pthread_cond_signal(&g->qcond)` 唤醒 GroupWait，但 `pthread_cond_signal` 只唤醒 **一个** waiter —— 如果此时有 idle worker 也在 `qcond` 上等待，signal 可能唤醒的是 idle worker 而不是 GroupWait 调用者，导致 GroupWait **永远阻塞**（lost wake-up）。

**修复方案**：

在 `xbase/task.c` 中新增独立的 `pthread_cond_t wcond`，专门给 `xTaskGroupWait()` 使用：

- `qcond` —— 仅用于 worker 等待新任务
- `wcond` —— 专用于 `xTaskGroupWait()` 等待所有任务完成

修改点：
- 结构体中新增 `wcond` 字段
- `xTaskGroupCreate()` 中初始化 `wcond`
- worker 完成最后一个任务时 signal `wcond`（而非 `qcond`）
- `xTaskGroupWait()` 在 `wcond` 上等待（而非 `qcond`）
- `xTaskGroupDestroy()` 中销毁 `wcond`

## 经验总结

1. **共享 condition variable 是并发 bug 的常见来源**：不同语义的等待者不应共用同一个 cond，否则 `pthread_cond_signal` 可能唤醒错误的 waiter
2. **verbose/日志输出会改变线程调度时序**：如果加了调试输出后 bug 消失，大概率是竞态条件，需要仔细审查同步原语
3. **CI 上的定时器测试需要留足余量**：毫秒级间隔在 CI 共享环境下容易因 CPU 调度抖动而失败
