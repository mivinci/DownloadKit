### 修复事件循环 dispatch 中的 use-after-free（xbase）

**问题**：`HttpClientTest.ConcurrentRequests` 测试偶发 Bus error / SEGFAULT（约 60% 复现率）。

**根因**：kqueue 的 `kevent()` 可以在一次调用中返回同一个 fd 的多个事件（如 `EVFILT_READ` + `EVFILT_WRITE`）。当第一个事件的回调触发 curl 的 `CURL_POLL_REMOVE` → `xEventDel` → `sources_remove` 时，`xEventSource_` 被立即 free。但同一批次中后续事件的 `udata` 仍指向已释放的内存，造成 use-after-free。

**修复**：将 `sources_remove` 改为延迟删除模式：

1. `xEventSource_` 新增 `deleted` 标志位
2. `sources_remove` 只标记 `deleted = 1`，不立即 free
3. dispatch 循环中跳过 `deleted` 的 source
4. 循环结束后由 `sources_sweep()` 统一释放已删除的 source

三个后端（kqueue、epoll、poll）均已修复。修复后连续 10+ 次测试全部通过。

## 经验总结

1. **compact 逻辑要仔细推导**：`buf_grow()` 的 compact 分支连续两轮 review 都没改对。第一轮把复杂表达式简化为 `needed <= buf->cap`，看似合理但和外层检查等价，仍是死代码。正确做法是 `unread + needed <= buf->cap`——compact 腾出的空间是 `rpos` 之前的部分，需要加上 unread 才是真实的空间需求判断。
2. **overlay 结构要注意字段覆盖**：`PoolNode_` overlay `xIOBlock`时，`next`指针会覆盖`refs`字段。在这种设计下不能对 pool 中 block 的`refs`做 assert 检查，只能通过文档约束 invariant。
3. **跨平台头文件不能依赖间接引入**：`SIZE_MAX` 在 macOS/Clang 下被其他头文件间接引入，但 Linux/GCC 严格模式下必须显式 `#include <stdint.h>`。CI 环境和本地环境的差异要注意。
4. **事件循环 dispatch 中不能立即释放 source**：kqueue/epoll 一次 `kevent()`/`epoll_wait()` 可能返回同一个 fd 的多个事件，如果回调中删除了 source 并立即 free，后续事件的 `udata` 就是悬空指针。正确做法是延迟删除——标记 + sweep。
