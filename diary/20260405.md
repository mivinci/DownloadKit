#### 核心实现

**1. 定义 `xHttpProto` vtable 接口（`server_private.h`）**

```c
typedef struct xHttpProto_ {
  int          (*on_data)(struct xHttpConn_ *conn, const char *buf, size_t len);
  void         (*reset)(struct xHttpConn_ *conn);
  void         (*destroy)(struct xHttpConn_ *conn);
  const char  *(*method)(struct xHttpConn_ *conn);
  int          (*should_keep_alive)(struct xHttpConn_ *conn);
  void         *state;
} xHttpProto;
```

用 `xHttpProto proto` 字段替换了 `xHttpConn_` 中原有的
`llhttp_t parser` 和 `llhttp_settings_t parser_settings`，
`server_private.h` 不再 `#include <llhttp.h>`。

**2. 实现独立的 HTTP/1.1 协议处理器（`proto_h1.c`）**

新建 `proto_h1.c` 和 `proto_h1.h`，包含：

- `xHttpProtoH1` 结构体
  （内含 `llhttp_t parser` + `llhttp_settings_t settings`）
- 从 `server.c` 搬迁的 6 个 llhttp 回调函数
  （`on_url`、`on_header_field`、`on_header_value`、
  `on_headers_complete`、`on_body`、`on_message_complete`）
- 5 个 vtable 方法实现
  （`h1_on_data`、`h1_reset`、`h1_destroy`、
  `h1_method`、`h1_should_keep_alive`）
- `xHttpProtoH1Init()` 初始化函数：堆分配 + 回调绑定 + vtable 填充

**3. 改造 `server.c` 调用点**

将 5 个 llhttp 直接调用点全部替换为 vtable 调用：

| 调用点 | Before | After |
| -------- | -------- | ------- |
| 初始化 | `llhttp_init()` + 手动设置回调 | `xHttpProtoH1Init(conn)` |
| 数据解析 | `llhttp_execute()` + 检查 error/complete | `conn->proto.on_data()` 三值返回 |
| 获取方法 | `llhttp_method_name(parser.method)` | `conn->proto.method(conn)` |
| 重置 | `llhttp_reset(&conn->parser)` | `conn->proto.reset(conn)` |
| 销毁 | 无 | `conn->proto.destroy(conn)` |

删除了 `server.c` 中的 6 个 llhttp 回调函数定义和
forward declarations，`server.c` 不再包含
`#include <llhttp.h>`。

After:   xHttpConn_ ──vtable──> xHttpProto ──state──> xHttpProtoH1 (堆分配)

## 经验总结（协议抽象层）

1. **vtable 抽象的粒度要恰到好处**：
   `xHttpProto` 只暴露了 5 个方法
   （`on_data`、`reset`、`destroy`、`method`、
   `should_keep_alive`），刚好覆盖 `server.c`
   中所有与协议相关的操作。请求解析状态
   （`url`、`headers_raw`、`body` 等）保留在
   `xHttpConn_` 中，因为这些是 HTTP/1.1 和
   HTTP/2 共有的通用属性。
2. **三值返回简化了调用方逻辑**：
   原来 `on_conn_event` 中需要分别检查
   `llhttp_execute` 的返回值、`pending_error`
   标志和 `request_complete` 标志，改为 `on_data`
   内部封装后只需判断
   `rc < 0 / rc > 0 / rc == 0`，代码更清晰。
3. **独立文件有利于后续扩展**：
   将 llhttp 回调放在独立的 `proto_h1.c` 中，
   未来添加 `proto_h2.c` 时只需实现相同的
   vtable 接口，`server.c` 无需任何改动。

### xhttp H2 流式响应实现

实现 H2 的流式响应（`write_data` + `end_stream`），使 SSE 等流式场景能在 H2C 上工作。

#### 设计方案

- 首次 `write_data` 调用提交 HEADERS + 一个 deferred data provider
- 后续调用将数据追加到 per-stream 的 `xIOBuffer`，
  并通过 `nghttp2_session_resume_data()`
  恢复 nghttp2 data provider
- `end_stream` 设置 EOF 标志并恢复，
  使 read callback 在最后一个 DATA frame 上
  返回 `NGHTTP2_DATA_FLAG_EOF`

| 文件 | 修改内容 |
| ------ | --------- |
| `xhttp/proto_h2.c` | 实现 `h2_write_data`、`h2_end_stream`，新增 deferred provider |

### H2 Body Use-After-Free 修复

#### 问题

`h2_send_response` 中 `h2_body_source.data`
直接指向调用方传入的 body 指针。
当调用方的 buffer 是栈分配的时，
在 `nghttp2_session_send()` 实际发送数据时
该指针已失效，导致 use-after-free。

#### 修复

将 body 数据 `malloc` 拷贝到堆上，`h2_body_read_callback` 在发送完毕（`EOF`）后 `free` 释放：

- `h2_body_source.data` 类型从 `const char *` 改为 `char *`（堆分配副本）
- `h2_send_response` 中 `malloc` + `memcpy` 拷贝 body
- `h2_body_read_callback` 在 `pos >= len` 时 `free(src->data)`

#### 涉及文件（Use-After-Free 修复）

| 文件 | 修改内容 |
| ------ | --------- |
| `xhttp/proto_h2.c` | 修复 `h2_body_source` 生命周期：堆拷贝 body + EOF 时释放 |

### H2 响应 Header 小写修复

#### 问题现象

HTTP/2 规范（RFC 9113 §8.2.1）要求
header name 必须全部小写。server 端 H2 响应
使用了混合大小写的 header name（如 `Content-Type`），
导致 curl/nghttp2 客户端拒绝响应。

#### 修复措施

在 `proto_h2.c` 中将 H2 响应的 header name 统一转为小写。

## 经验总结（Client H2 & 集成测试）

1. **H2 响应 header 必须小写**：
   HTTP/2 规范要求 header field name 全部小写，
   混合大小写会被严格的客户端（如 nghttp2）拒绝。
   这是从 HTTP/1.1 迁移到 HTTP/2 时容易遗漏的细节。
2. **Body 生命周期要注意**：
   nghttp2 的 data provider 是异步回调模式，
   body 数据在 `nghttp2_session_send()` 时
   才真正被读取。如果 body 来自栈上的临时 buffer，
   必须堆拷贝以避免 use-after-free。
3. **集成测试的价值**：
   client↔server 联合测试比单独的 server 测试
   更能发现协议兼容性问题
   （如 header 大小写、body 生命周期），
   20 个测试覆盖了 H1/H2 的各种场景组合。
4. **Edge-triggered I/O 的权衡**：
   理论上应该 drain 到 EAGAIN，
   但实际要看下游代码是否支持。
   当前的 linearize + consume-all 模式不适合 drain，
   需要先重构为增量解析才能安全地改为 drain 循环。

### Transport 层代码规范化

#### 1. `transport.h` 宏定义改造

将 `transport.h` 中的结构体和枚举改为使用 `xbase/base.h` 的宏定义：

- 新增 `#include <xbase/base.h>`
- 匿名枚举 → `XDEF_ENUM(xHttpTransportResult){...};`
- `typedef struct xHttpTransport_ {...} xHttpTransport;` → `XDEF_STRUCT(xHttpTransport){...};`

#### 2. 枚举命名规范修正

枚举值从全大写风格改为项目规范的 `类型名_PascalCase` 风格：

| 旧命名 | 新命名 |
| ------ | ------ |
| `XHTTP_TRANSPORT_DONE` | `xHttpTransportResult_Done` |
| `XHTTP_TRANSPORT_WANT_READ` | `xHttpTransportResult_WantRead` |
| `XHTTP_TRANSPORT_WANT_WRITE` | `xHttpTransportResult_WantWrite` |
| `XHTTP_TRANSPORT_ERROR` | `xHttpTransportResult_Error` |

涉及 4 个文件：`transport.h`、`server.c`、
`transport_tls_openssl.c`、`transport_tls_mbedtls.c`。

#### 3. `transport_private.h` 创建与头文件重构

创建 `transport_private.h`，将内部 transport 函数声明集中管理：

- `xHttpTransportPlainInit`（从 `transport.h` 移入）
- TLS 后端函数（从 `server.c` 的裸 `extern` 声明移入）：
  `xHttpTlsCtxCreate*`、`xHttpTlsCtxDestroy*`、`xHttpTlsTransportInit*`

同时：
- `transport.h` 删除 `xHttpTransportPlainInit` 声明，公共头文件只保留类型定义
- `server.c` 删除 6 个裸 `extern` 声明，改为 `#include "transport_private.h"`

#### 4. Transport 实现文件 include 修复

三个实现文件改为 `#include "transport_private.h"` 替代 `#include "transport.h"`，
确保编译器能检查函数声明与定义的一致性：

- `transport_plain.c`
- `transport_tls_openssl.c`
- `transport_tls_mbedtls.c`

## 经验总结（代码规范化）

1. **公共头文件应只暴露类型定义**：
   `transport.h` 作为公共头文件，只应包含
   `xHttpTransportResult` 枚举和 `xHttpTransport` 结构体。
   初始化函数（`PlainInit`、`TlsInit`）是模块内部 API，
   应放在 `transport_private.h` 中。
2. **实现文件应 include 自己的声明头文件**：
   `.c` 文件 include 包含自身函数声明的头文件，
   编译器能自动检查签名一致性，
   避免后续改签名时漏改的问题。
3. **枚举命名要统一**：
   项目规范是 `类型名_PascalCase`（如 `xErrno_Ok`、`xEvent_Read`），
   新增枚举应遵循同样的模式，
   避免混入全大写 `XHTTP_TRANSPORT_*` 风格。
4. **定期 clang-format**：
   多人协作或大量修改后，
   统一执行一次 clang-format 能消除格式不一致，
   减少 code review 中的噪音。
