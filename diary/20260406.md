### 2. 修复 WebSocket 连接 segfault（use-after-free）

**问题现象**：`ws_echo_server` 启动后，客户端连接再关闭，服务端过一会报 segmentation fault。

**排查过程**：

- 先在 example 中加了 crash 信号处理器（SIGSEGV/SIGABRT/SIGBUS），用 `backtrace()` 打印堆栈
- 分析代码发现 HTTP accept 时设置了 60s idle timeout（`xSocketSetTimeout`），WebSocket upgrade 后 WS 层换了回调但没有清除 socket 内部的 read timer

**根因分析**：

- HTTP 层的 `read_timeout_cb` 在 socket 内部仍然存活
- WS 连接关闭后 socket 被 destroy，但如果 timer 已经被 event loop 调度，会访问已 free 的内存
- 本质是 **use-after-free**：两套 timer（HTTP 层 + WS 层）同时存在，生命周期管理冲突

**修复方案**：

- 在 `xWsConnCreate`（`xhttp/ws.c`）中，接管 socket 后立即调用 `xSocketSetTimeout(sock, 0, 0)` 清除 HTTP 层遗留的 read/write timeout timer
- WS 层自己通过 `xEventLoopTimerAfter` 管理 idle timer，不依赖 socket 层的 timeout 机制

### 5. 修复 CI 流水线失败

**问题一：`-Wsign-compare` 编译错误**

CI 使用 `-Wall -Wextra -Werror`，`-Wsign-compare` 将有符号/无符号整数比较视为错误。

- `xbase/log_test.cpp`：`captured.msg.size()`（`size_t`）与 `XLOG_BUF_SIZE - 1`（`int`）比较
- `xbase/task_test.cpp`：`xTaskGroupThreads()`/`xTaskGroupPending()`（`size_t`）与 `0`/`1`/`6`（`int`）比较

修复：将所有与 `size_t` 返回值比较的整数字面量显式转换为 `(size_t)`。

**问题二：ASan 检测到 `ws_on_event` 中的 heap-use-after-free**

- 测试用例：`WsServerTest.CloseHandshake`
- 根因：`ws_fire_close()` 内部直接调用 `xWsConnDestroy()` 释放连接，但调用者 `ws_on_event()` 在同一次事件循环迭代中可能继续访问已释放的 `conn`（例如 epoll 同时返回 Write + Read 事件，或帧解析循环中处理 Close 帧后继续循环）
- 修复：将 `xWsConnDestroy` 从 `ws_fire_close()` 中移出，改为在 `ws_on_event()` 末尾通过 `goto destroy` 统一处理。每次可能触发 `XWS_CLOSED` 状态转换的调用后，检查 `close_state` 并跳转到 destroy 标签。对于独立定时器回调 `ws_idle_timeout`（不经过 `ws_on_event`），在其等待对端响应超时的分支中保留 `xWsConnDestroy` 调用。

**问题三：macOS mbedTLS 4.x 编译失败 — `sha1.h` not found**

- 根因：Homebrew 上 mbedTLS 已升级到 4.1.0，该版本移除了独立的 `mbedtls/sha1.h` 头文件，SHA-1 功能被整合到通用的 `mbedtls/md.h`（Message Digest）API 中
- 修复：在 `ws_crypto_mbedtls.c` 中使用 `__has_include(<mbedtls/sha1.h>)` 检测头文件是否存在：
  - 存在（2.x/3.x）：使用 `mbedtls_sha1()` / `mbedtls_sha1_ret()`
  - 不存在（4.x）：使用 `mbedtls_md()` + `MBEDTLS_MD_SHA1`
- 附带修复：mbedTLS 4.x 的 `mbedtls_base64_encode` 对空输入不再写入 null terminator，在 `xWsBase64Encode` 中显式处理 `in_len == 0` 的情况

### 13. WebSocket 客户端（`xWsConnect`）

实现全异步 WebSocket 客户端连接状态机
（`xhttp/ws_connect.c`），流程：

```text
URL parse → DNS → TCP → [TLS] → HTTP Upgrade → xWsConn
```

- 支持 `ws://` 和 `wss://`（TLS）协议
- 5 阶段状态机：DNS → TCP_CONNECT →
  TLS_HANDSHAKE → HTTP_UPGRADE_WRITE →
  HTTP_UPGRADE_READ → DONE
- 默认 10s 连接超时，最大 4096 字节响应头缓冲
- 复用服务端的 `xWsConn` 和 `xWsCallbacks`，
  客户端/服务端共享同一套帧处理和回调机制

**客户端握手**（`ws_handshake_client.h/c`）：

- `xWsClientBuildUpgradeRequest`：构建 HTTP/1.1
  Upgrade 请求，生成随机 Sec-WebSocket-Key
- `xWsClientValidateUpgradeResponse`：验证 101
  响应的 Upgrade / Connection / Accept 头

**TLS 客户端传输层**
（`transport_tls_client_mbedtls.c` /
`transport_tls_client_openssl.c`）：

- 新增 `transport_tls_client.h` 接口
- mbedTLS 和 OpenSSL 双后端实现
- 同时将原有 TLS 文件重命名加 `_server` 后缀

## 经验总结

1. **接管 socket 时必须清理前一层的状态**：WebSocket upgrade 本质是"连接劫持"，从 HTTP 层接管 socket 后，必须清除 HTTP 层遗留的 timer、buffer 等状态，否则两套生命周期管理会冲突，导致 use-after-free。
2. **crash 堆栈打印应该作为基础设施**：封装成 `xPrintBacktraceOnCrash()` 后，任何程序只需一行代码就能获得 crash 诊断能力，大幅降低排查成本。
3. **信号处理器中要用 async-signal-safe 的函数**：`bt_capture` 内部使用 `snprintf` 严格来说不是 async-signal-safe 的，但在 crash handler 中可以接受（程序已经要挂了）。未来可以考虑用 `write()` 直接输出。
4. **事件回调中不要在中间销毁自身**：当一个事件回调函数可能触发多个子操作（如同时处理 Write + Read），任何子操作中的销毁都会导致后续子操作访问已释放内存。正确做法是标记状态，延迟到回调末尾统一销毁。
5. **CI 的 `-Werror` 是好习惯**：它能在编译期捕获潜在的类型安全问题（如有符号/无符号比较），但需要确保测试代码也遵守同样的严格标准。
6. **依赖库大版本升级要关注 API 变化**：mbedTLS 4.x 移除了多个独立的哈希头文件（sha1.h、sha256.h 等），统一到 md.h API。使用 `__has_include` 做编译期检测是兼容多版本的好方法。
7. **C 库 API 设计：配置结构体优于多个 setter**：将 TLS、HTTP 版本等配置合并到 `xHttpClientConf`，在 `Create` 时一次性传入，比分散的 `SetTls` / `SetHttpVersion` 更简洁、更不容易出错。零初始化 `{0}` 即为全默认，`NULL` conf 也是全默认，向后兼容友好。
8. **便利函数的内存管理要跟宿主对象绑定**：`xWsServe` 内部分配的 `xWsServeCtx` 通过 server 的 `aux_data` / `aux_free` 机制在 `xHttpServerDestroy` 时自动释放，避免用户忘记手动清理。这种"附属数据随宿主销毁"的模式在 C 库中很实用。
9. **mermaid 中含下划线的标识符要加引号**：
  `participant X as foo_bar` 在某些 mermaid
  版本中会把下划线解析为 markdown 斜体标记，
  导致语法错误。加引号 `"foo_bar"` 可以避免。
10. **压缩扩展要用编译开关隔离**：
  permessage-deflate 依赖 zlib，不是所有环境都
  需要。用 `XHTTP_WS_DEFLATE` 宏控制编译，
  头文件和实现都用 `#ifdef` 包裹，零成本抽象。
11. **异步连接状态机要用枚举阶段管理**：
  WebSocket 客户端连接经历 DNS → TCP → TLS →
  HTTP Upgrade 多个阶段，用 `xWsConnectPhase`
  枚举 + 统一的 connector 结构体管理状态转换，
  比嵌套回调更清晰、更容易调试。
12. **TLS 配置应放在网络层而非应用层**：
  将 `xTlsClientConf` / `xTlsServerConf` 从
  xhttp 移到 xnet，使 WebSocket 客户端等模块
  可以直接复用，避免循环依赖。
