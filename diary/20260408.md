# 2026-04-08 日报

## 今日工作

### 1. 修复 HTTP Server 路由匹配不支持 Query String

**问题现象**：HTTP bench server 的 `/echo?size=N` 路由返回 404，而 `/echo` 不带参数可以正常工作。

**排查过程**：

- 使用 `curl -sv "http://127.0.0.1:9090/echo?size=64"` 确认返回 404
- 定位到 `xhttp/server.c` 中的 `route_match` 函数
- 发现 URL segment 解析循环 `while (*p && *p != '/')` 没有在 `?` 处停止
- 当 URL 为 `/echo?size=64` 时，最后一个 segment 被解析为 `echo?size=64`，与路由 pattern 中的 `echo` 不匹配

**根因分析**：

`route_match` 函数在逐段匹配 URL 时存在两个缺陷：

1. segment 解析循环只以 `/` 和 `\0` 作为分隔符，没有考虑 `?` 作为 query string 的起始标记
2. 末尾检查 `if (*p != '\0') return 0` 没有允许 URL 以 `?` 开头的 query string 结尾

**修复方案**：

- `xhttp/server.c` `route_match` — segment 解析循环增加 `&& *p != '?'` 条件
- 末尾检查改为 `if (*p != '\0' && *p != '?') return 0`，允许 query string 尾部

**验证**：`/echo?size=128` 返回 128 字节，`/echo?size=1024` 返回 1024 字节，`/ping` 不受影响。

### 2. 修复 HTTP Server 大 POST Body 请求挂起

**问题现象**：POST body 大于约 8KB 时，请求永远无法完成（curl 超时，wrk 报 socket errors）。4KB、6KB、7KB 正常，7.9KB 开始失败。

**排查过程**：

- 使用 curl 发送不同大小的 POST body 进行二分定位，确认边界在 header + body 总计 ~8KB 处
- 分析 `on_conn_event` 函数，发现每次事件只调用一次 `xIOBufferReadWith`，最多读取 `XIOBUFFER_BLOCK_SIZE`（8KB）
- 检查 kqueue 事件注册代码，确认使用 `EV_CLEAR`（edge-triggered 模式）

**根因分析**：

在 edge-triggered 模式（kqueue `EV_CLEAR` / epoll `EPOLLET`）下，socket 上的可读事件只在**新数据到达**时触发一次。如果一次 `read()` 没有读完 socket buffer 中的所有数据，不会再触发新事件。

`on_conn_event` 中每次事件只调用一次 `xIOBufferReadWith`（最多读 8KB），当 HTTP 请求的 header + body 超过 8KB 时：

1. 第一次读取只能读到部分数据（8KB）
2. llhttp 解析后返回 `rc == 0`（需要更多数据）
3. 函数直接返回，等待下一次事件
4. 但 socket buffer 中仍有未读数据，edge-triggered 模式不会再次通知
5. 请求永远无法完成 → 连接挂起

**修复方案**：

将 `on_conn_event` 中的单次读取改为 `for(;;)` drain loop：

- 每次迭代：读一个 chunk → 喂给 parser → 消费已读数据
- `rc > 0`（请求完成）→ dispatch 并返回
- `rc < 0`（解析错误）→ 发送错误响应并返回
- `rc == 0` 且 `n < 0`（EAGAIN）→ socket 无更多数据，等待下一次事件
- `rc == 0` 且 `n > 0` → 继续循环读取下一个 chunk

这样保持了每次只分配一个 block 的内存特性（峰值内存 ~1 block），同时正确处理了 edge-triggered 模式下的大请求。

**验证**：8KB、16KB、64KB、256KB POST body 全部正常返回。wrk 压测 16KB POST 达到 78.7K req/s，64KB POST 达到 35K req/s。

### 3. HTTP Server 端到端 Benchmark

修复上述两个问题后，对 HTTP bench server 进行了完整的端到端压测（xKit vs Go），覆盖三种协议：

**HTTP/1.1**（wrk）：xKit 单线程 event-loop 在 GET /ping 上达到 152K req/s，比 Go 快 18–24%。POST /echo 64KB 达到 2.20 GB/s 传输速率。

**HTTP/2 h2c**（h2load）：得益于 HTTP/2 stream multiplexing，xKit 吞吐量从 HTTP/1.1 的 152K 跃升至 576K req/s（+269%），而 Go 基本持平。xKit 在 GET /ping 上领先 Go +294%~+405%，优势远大于 HTTP/1.1。

**HTTPS**（wrk + h2load）：

- HTTPS/1.1 下 xKit 与 Go 基本持平（~125K req/s），TLS 加密成为瓶颈，单线程 OpenSSL 抹平了 HTTP 层优势
- HTTPS/2 下 xKit 重新拉开差距（+209%~+278%），stream multiplexing 分摊了 TLS 开销
- 64KB 大 payload POST 是唯一 Go 胜出的场景（+46%），因为 Go 多核并行 TLS 加密更高效

所有 benchmark 结果已整理为独立文档页面（`docs/bench/`），并在 SUMMARY.md 中新增 Benchmark 板块。

## 经验总结

- Edge-triggered I/O 模式下必须 drain until EAGAIN，否则 socket buffer 中的残留数据不会触发新事件，导致请求挂起。这是 edge-triggered 模式最常见的陷阱之一。
- 路由匹配必须在解析 URL path 时剥离 query string，这是 HTTP 路由系统的基本要求。RFC 3986 明确规定 `?` 是 path 和 query 的分隔符。
- 二分法定位边界问题非常有效：通过逐步增大 POST body 大小，快速定位到 8KB 的 block size 边界。
