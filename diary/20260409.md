### 1. 修复 task.c use-after-free（CI ASan 报错）

**问题现象**：PR `codebuddy/fix-ws-drain-loop` 的 CI 流水线在 Linux ASan 构建下报 `heap-use-after-free`，崩溃点在 `worker_loop`（task.c:125），写入已被 `xTaskWait` 释放的 task 对象。

**排查过程**：

- 分析 ASan 堆栈：T11（worker 线程）在 `worker_loop` task.c:125 写 `task->next`，T0（主线程）在 `xTaskWait` task.c:332 已经 `free(task)`
- 梳理 `worker_loop` 的执行顺序：先 broadcast `task->cond`（标记 done），再追加到 done_list（写 `task->next`）
- 梳理 `xTaskWait` 的执行顺序：被 broadcast 唤醒后立刻 `free(task)`

**根因分析**：

`worker_loop` 中操作顺序存在竞态条件：

```text
原来的顺序（有 bug）：
1. lock task->lock → set done=true → broadcast → unlock   ← xTaskWait 被唤醒
2. lock g->qlock → task->next = NULL → 追加到 done_list   ← 💥 task 已被 free
3. 更新 pending 计数器
```

`xTaskWait` 在步骤 1 的 broadcast 后被唤醒，立刻 `free(task)`。但 worker 线程在步骤 2 还要写 `task->next = NULL`，触发 heap-use-after-free。

**修复方案**：

调换步骤 1 和 2 的顺序——**先追加到 done_list，再标记 done + broadcast**：

```text
修复后的顺序：
1. lock g->qlock → task->next = NULL → 追加到 done_list → unlock
2. lock task->lock → set done=true → broadcast → unlock   ← xTaskWait 被唤醒
3. 更新 pending 计数器（只访问 group 级别的 atomic，不碰 task）
```

锁顺序无循环依赖（worker: qlock → task->lock，waiter: task->lock → qlock），不会死锁。

**验证**：本地 194 个测试全部通过。推送后 CI 流水线通过，PR 合入 main。

### 3. WebSocket Benchmark 测试与文档

完成了 WebSocket echo server 的端到端 benchmark，对比 xKit（单线程 event loop）与三个主流 Go WebSocket 库（gorilla/websocket、nhooyr/websocket、gobwas/ws）。

**测试内容**：

- **WS（明文）**：64B/256B/1KB/4KB 消息 × 50/100/200/500 连接数
- **WSS（TLS）**：同上参数，使用自签名证书（RSA 2048, TLSv1.3）

**关键结论**：

| 场景 | xKit | gorilla（最快 Go 库） | 差距 |
| --- | ---: | ---: | --- |
| WS 64B, 100 conns | 219,813 msg/s | 180,373 msg/s | xKit **+22%** |
| WS 4KB, 100 conns | 133,553 msg/s (1.02 GB/s) | 125,313 msg/s | xKit **+7%** |
| WSS 64B, 50 conns | 186,513 msg/s | 173,125 msg/s | xKit **+8%** |
| WSS 64B, 500 conns | 167,019 msg/s | 184,532 msg/s | gorilla **+10%** |
| WSS 4KB, 100 conns | 92,686 msg/s | 137,560 msg/s | gorilla **+48%** |

- 明文 WS 场景下 xKit 全面领先，吞吐量在 50~500 连接间几乎无衰减（<1%）
- WSS 场景下低连接数 xKit 仍领先，但 200+ 连接时 gorilla 反超——Go 的 per-goroutine `crypto/tls` 可并行加解密，而 xKit 单线程 OpenSSL 串行处理成为瓶颈
- TLS 对 xKit 的吞吐影响约 25%，对 Go 库几乎无影响

**涉及文件**：benchmark server（`bench/ws_bench_server.cpp`、`bench/wss_bench_server.cpp`）、Go 对比 server（gorilla/nhooyr/gobwas 各 WS+WSS 版本）、benchmark client（`bench/ws_bench_client.go`）、结果文档（`docs/bench/ws_server.md`）

## 经验总结

- 多线程代码中，**操作顺序决定正确性**。broadcast/signal 唤醒其他线程后，当前线程不应再访问可能被唤醒线程释放的对象。原则：先完成所有对共享对象的写操作，再通知其他线程。
- 推送到 GitHub 时注意 refspec 格式：`git push <remote> <local-branch>:<remote-branch>`，remote 名不应出现在 remote-branch 路径中，否则会创建多余的层级。
- 分析竞态条件时，画时序图（sequence diagram）非常有效，能直观展示多线程间的交错执行路径。
