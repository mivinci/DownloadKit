### 1. PR #76 — xNote + TLS freelist + xMpsc done-queue (`8eaf7a0`)

**问题现象**：`xTask` 每个任务需要分配 `pthread_mutex_t` + `pthread_cond_t`（~136 字节），submit/wait 路径上有大量 syscall 开销。

**修复方案**：

- **xNote**：新增轻量级 one-shot 通知原语（仅 4 字节），采用三级等待策略：
  1. 单次 atomic load（零开销快速路径）
  2. 64 次自旋 + CPU pause/yield（~1μs）
  3. 内核辅助等待（Linux futex / macOS __ulock）
- **TLS freelist**：为每个线程维护 task 结构体缓存，消除 submit-then-wait 路径上的 malloc/free
- **xMpsc done-queue**：用 lock-free MPSC 队列替换 mutex 保护的 done list，worker 完成任务时无需竞争 qlock

**效果**：`xTask_` 从 ~136 字节缩减到 ~48 字节；FanOut/100 吞吐 +37.3%，WorkerScaling/8 吞吐 +49.0%

**涉及文件**：`xbase/note.h`、`xbase/task.c`、`xbase/task.h`、`xbase/mpsc.c`、`xbase/mpsc.h`

### 4. PR #79 — Event Loop wake 机制 + timer dispatch 优化 (`0e823e2`)

**优化内容**：

#### 4a. Wake 机制优化

- kqueue 后端改用 `EVFILT_USER` 替代 pipe，epoll 后端改用 `eventfd`
- 新增 **wake coalescing**：通过 atomic `wake_pending` flag，多个 offload worker 并发完成时只有第一个执行 wake syscall，后续 worker 跳过。批量完成场景下 wake syscall 从 N 次降为 1 次

#### 4b. Timer dispatch 优化

- 批量弹出：单次加锁取出所有到期 timer，解锁后再逐个回调，消除 N 次 lock/unlock
- Timer 结构体 freelist（最多缓存 256 个），消除每次 submit/fire 的 malloc/free
- 提取公共 `loop_fire_expired_timers()` 到 `event_private.h`，消除 kqueue/epoll/poll 三后端的重复代码

**Benchmark 提升**（TimerBatch, CPU time）：

- Batch/10: 3794ns → 3419ns (~10% faster)
- Batch/100: 31479ns → 28236ns (~10% faster)
- Batch/1000: 318805ns → 296059ns (~7% faster)

#### 4c. Treiber stack freelist 回退

尝试将 work item freelist 改为 TLS 方案，发现 offload 场景下 alloc/free 跨线程（loop 线程分配、worker 线程释放），TLS 不适用，回退为 Treiber stack。

**涉及文件**：`xbase/event_kqueue.c`、`xbase/event_epoll.c`、`xbase/event_poll.c`、`xbase/event_private.h`、`xbase/event_timer.c`

#### 7e. mbedTLS DTLS 握手递归问题修复

**问题现象**：mbedTLS 后端的 DTLS 握手测试全部失败，双方卡在 Connecting 状态。

**排查过程**：
1. 添加 fprintf 调试日志，发现 `drive_handshake` 被无限递归调用
2. 分析递归路径：mbedTLS 的 `mbedtls_ssl_handshake` 在执行过程中同步调用 send callback → 对方 `FeedInput` → 对方 `drive_handshake` → 对方 `handshake` → 对方 send callback → 当前 `FeedInput` → 递归
3. 第一版修复（`driving` 标志阻止递归）导致 OpenSSL 后端也失败——因为 OpenSSL 的 `flush_bio_out` 也在 `handshake()` 内部调用 send callback
4. 分析 OpenSSL 失败原因：Passive 的 `flush_bio_out` 触发 Active 处理并回传数据，但 Passive 的 `driving=true` 阻止了后续处理，`SSL_do_handshake` 第二次调用时返回 `SSL_ERROR_SYSCALL`

**根因**：两个后端的发送机制不同——mbedTLS 在 `handshake()` 内部内联发送，OpenSSL 在 `handshake()` 内部通过 `flush_bio_out` 发送。两者都会在 loopback 场景下触发递归。

**最终修复方案**（三层修改）：
1. **`dtls_backend.h`**：新增可选的 `flush_output` 接口，将 OpenSSL 的 flush 从 `handshake()` 中分离
2. **`dtls_openssl.c`**：`openssl_handshake` 不再调用 `flush_bio_out`（握手完成时除外），新增 `openssl_flush_output` 方法
3. **`dtls_transport.c`**：
   - 添加 `driving` + `feed_while_driving` 双标志
   - `drive_handshake` 中：设置 `driving=true` 防止递归；`handshake()` 返回后调用 `flush_output()`（在 driving 保护下）；`Again` 时检查 `feed_while_driving` 决定是否继续循环
   - `FeedInput` 中：`driving=true` 时只写入数据并设置 `feed_while_driving=true`，不调用 `drive_handshake`
4. **`dtls_mbedtls.c`**：`.flush_output = NULL`（内联发送，无需 flush）

**验证**：OpenSSL 156/156 通过，mbedTLS 156/156 通过。

## 经验总结

1. **TLS freelist 不适用于跨线程 alloc/free 模式**：offload 场景下分配在 loop 线程、释放在 worker 线程，TLS 缓存无法跨线程共享，必须用 Treiber stack 等全局无锁结构
2. **Wake coalescing 是批量场景的关键优化**：多个 worker 并发完成时，atomic flag 可以将 N 次 wake syscall 降为 1 次
3. **Timer 批量弹出消除锁竞争**：单次加锁取出所有到期 timer 比逐个 pop 高效得多
4. **异步 TLS offload 对小消息不划算**：线程调度开销 > 加密 CPU 开销，65-70% 回退
5. **Benchmark 要控制环境变量**：同一设备不同时间跑出的绝对值可能差异很大，相对排名更有参考价值
6. **TLS 后端的 I/O 模型差异需要在 transport 层抽象**：OpenSSL 用 memory BIO 缓冲输出需要显式 flush，mbedTLS 通过回调内联发送。将 flush 从 handshake 中分离为独立接口是解决递归问题的关键
7. **loopback 测试中同步 send callback 会触发递归**：需要 re-entrancy guard（`driving` 标志）+ 延迟驱动（`feed_while_driving` 标志）来打破递归链
8. **CI 跨平台编译差异要注意**：GCC 比 clang 更严格（`-Wsign-compare`），不同版本的 mbedTLS API 签名不同（2.x `void` vs 3.x `int`），本地通过不代表 CI 通过
