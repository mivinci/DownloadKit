### 1. PeerConnection 需求概述

#### 1a. 架构设计

实现了完整的 WebRTC DataChannel 协议栈，分为五层：

```text
┌─────────────────────────────┐
│   xPeerConnection           │  顶层 API，编排整个协议栈
├─────────────────────────────┤
│   xDataChannel (DCEP)       │  RFC 8832 — 消息通道
├─────────────────────────────┤
│   xSctpTransport (usrsctp)  │  RFC 4960 — 可靠/不可靠传输
├─────────────────────────────┤
│   xDtlsTransport            │  RFC 6347 — DTLS 1.2 加密
├─────────────────────────────┤
│   xIceAgent (STUN/TURN)     │  RFC 8445 — NAT 穿透
└─────────────────────────────┘
```

API 设计对齐浏览器 `RTCPeerConnection`：`createOffer` / `createAnswer` / `setLocalDescription` / `setRemoteDescription` / `addIceCandidate` / `createDataChannel`。

### 2. PR #84 合入 main 过程中的 CI 修复

将 `codebuddy/peer-connection` 分支合入 main 时，修复了 6 个 CI 编译问题：

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| usrsctp 依赖缺失 | CI 未安装 usrsctp | Ubuntu 源码编译，macOS `brew install libusrsctp` |
| GCC sign-compare | `int` vs `size_t` 比较 | `(size_t)12` 显式转型 |
| mbedTLS 2.x sha256 | deprecated API 返回 void | 版本判断用 `mbedtls_sha256_ret` |
| mbedTLS DTLS 握手递归 | send callback 同步触发无限递归 | `driving` + `feed_while_driving` 双标志 |
| OpenSSL 握手失败 | flush 在 handshake 内部触发递归 | 将 `flush_bio_out` 分离为独立的 `flush_output` 接口 |
| macOS 头文件不同步 | 本地改动未推送 | 提交所有改动 |

#### 2a. 重点问题：mbedTLS/OpenSSL DTLS 握手递归

**问题现象**：mbedTLS 后端的 DTLS 握手测试全部失败，双方卡在 Connecting 状态。

**排查过程**：

1. 添加 fprintf 调试日志，发现 `drive_handshake` 被无限递归调用
2. 分析递归路径：mbedTLS 的 `mbedtls_ssl_handshake` 在执行过程中同步调用 send callback → 对方 `FeedInput` → 对方 `drive_handshake` → 对方 `handshake` → 对方 send callback → 当前 `FeedInput` → 递归
3. 第一版修复（`driving` 标志阻止递归）导致 OpenSSL 后端也失败——因为 OpenSSL 的 `flush_bio_out` 也在 `handshake()` 内部调用 send callback

**根因**：两个后端的发送机制不同——mbedTLS 在 `handshake()` 内部内联发送，OpenSSL 在 `handshake()` 内部通过 `flush_bio_out` 发送。两者都会在 loopback 场景下触发递归。

**最终修复方案**（三层修改）：

1. **`dtls_backend.h`**：新增可选的 `flush_output` 接口，将 OpenSSL 的 flush 从 `handshake()` 中分离
2. **`dtls_openssl.c`**：`openssl_handshake` 不再调用 `flush_bio_out`（握手完成时除外），新增 `openssl_flush_output` 方法
3. **`dtls_transport.c`**：添加 `driving` + `feed_while_driving` 双标志，`FeedInput` 中 `driving=true` 时只写入数据并设置 `feed_while_driving=true`，不调用 `drive_handshake`

**验证**：OpenSSL 156/156 通过，mbedTLS 156/156 通过。

## 经验总结

1. **协议栈分层设计是关键**：ICE → DTLS → SCTP → DataChannel 四层各自独立，通过回调串联。每层可独立测试，降低了调试复杂度
2. **可插拔后端需要统一抽象**：OpenSSL 和 mbedTLS 的 I/O 模型差异（memory BIO vs 回调内联发送）需要在 transport 层通过 `flush_output` 接口统一
3. **loopback 测试中同步 send callback 会触发递归**：需要 re-entrancy guard（`driving` 标志）+ 延迟驱动（`feed_while_driving` 标志）来打破递归链
4. **CI 跨平台编译差异要注意**：GCC 比 clang 更严格（`-Wsign-compare`），不同版本的 mbedTLS API 签名不同（2.x `void` vs 3.x `int`），本地通过不代表 CI 通过
5. **SDP 是 WebRTC 的"胶水"**：所有协议参数（ICE credentials、DTLS fingerprint、SCTP port）都通过 SDP 交换，SDP 解析的正确性直接决定握手成败
